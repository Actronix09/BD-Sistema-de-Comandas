# Reglas de Transformación del Modelo EER al Modelo Relacional

En este documento se aplican, una por una, las reglas de transformación al modelo EER del sistema de comandas: primero las de entidades y atributos (Parte 3), después las de relaciones (Parte 4) y al final las de entidades débiles y jerarquías (Parte 5). Cada decisión indica la regla que la origina y la tabla resultante. El código que implementa todo esto es [`sql/esquema.sql`](<../sql/esquema.sql>), documentado en la Parte 6.

---

**Cliente:** Salón de eventos — sistema de comandas

**Modelo de origen:** [Modelo Entidad-Relación Extendido](<ModeloEntidadRelaciónExtendido.md>) · [Inventario del Modelo EER](<InventarioModeloEER.md>)

**Gestor:** PostgreSQL 16

**Contenido:** Reglas 1 a 9 aplicadas a cada elemento del inventario, tipos de dato elegidos, acciones referenciales, estrategia para la jerarquía de Usuario y lo que el esquema no puede garantizar.

---

## Notación

Cada tabla resultante se escribe como `tabla (columnas)`, con la clave primaria <ins>subrayada</ins> y las claves foráneas en *cursiva* seguidas de la tabla a la que apuntan: *id_mesero* → mesero.

## Decisiones de tipos de dato

Antes de las reglas conviene fijar qué tipo recibe cada clase de atributo, para no justificarlo tabla por tabla:

| Clase de atributo | Tipo en PostgreSQL | Por qué |
| :-- | :-- | :-- |
| Identificadores (ID, número de evento, número de pago) | `INTEGER GENERATED BY DEFAULT AS IDENTITY` | El gestor asigna el siguiente número con una secuencia interna de la propia columna. `BY DEFAULT` permite cargar números conocidos (el evento 17), pero hacerlo no avanza la secuencia, así que `datos-ejemplo.sql` termina con `setval` para que la siguiente alta no choque. |
| Claves parciales (número de mesa, secuencial) | `SMALLINT` | Se reinician en cada evento y el salón tiene alrededor de 20 mesas y 60 cuentas por evento |
| Dinero (precio, monto, propina) | `NUMERIC(10,2)` | Decimal exacto. Con `REAL` o `DOUBLE PRECISION` las sumas de centavos acumulan error |
| Cantidades de inventario (stock, cantidad por porción) | `NUMERIC(10,3)` | Decimal exacto en la unidad base del ingrediente (gramos, mililitros o piezas); tres decimales alcanzan para fracciones de porción sin que el stock acumule error al restar |
| Valores de una lista cerrada (estado, categoría, forma de pago, rol) | `VARCHAR(n)` con `CHECK (... IN (...))` | La lista queda visible en el diccionario y se amplía con un `ALTER TABLE`; un `ENUM` no permite quitar valores |
| Fechas | `DATE` | Rechaza fechas imposibles como el 31 de febrero |
| Time Stamp | `TIMESTAMPTZ` | Guarda el instante exacto; los componentes se calculan en la hora de la Ciudad de México |
| Contraseña | `VARCHAR(255)` llamado `contrasena_hash` | Nunca se guarda la contraseña en claro, solo su hash |
| Textos libres | `VARCHAR(n)` | El límite evita que un error de captura meta un texto de miles de caracteres |

# Parte 3 — Reglas de transformación básicas

## Regla 1: entidades fuertes

> Toda entidad fuerte se transforma en una tabla. Cada atributo simple pasa a ser una columna con su tipo, el identificador se declara como clave primaria y se agregan las restricciones que correspondan.

Las ocho entidades fuertes del inventario producen ocho tablas. Aquí se muestran solo sus atributos propios; las claves foráneas que reciben por sus relaciones se agregan en la Parte 4.

| Entidad | Tabla resultante | Clave primaria |
| :-- | :-- | :-- |
| Evento | **evento** (<ins>numero_evento</ins>, fecha, tipo_evento, numero_asistentes, estado) | `numero_evento` |
| Usuario | **usuario** (<ins>id_usuario</ins>, nombre, usuario, fecha_nacimiento, contrasena_hash, rol) | `id_usuario` |
| Producto | **producto** (<ins>id_producto</ins>, nombre, descripcion, categoria, precio) | `id_producto` |
| Comanda | **comanda** (<ins>id_comanda</ins>, fecha_hora, precio_cobrado, estado, detalles) | `id_comanda` |
| Pago | **pago** (<ins>numero_pago</ins>, monto, forma_pago, fecha_hora) | `numero_pago` |
| Anticipo | **anticipo** (<ins>id_anticipo</ins>, monto, fecha) | `id_anticipo` |
| Paquete | **paquete** (<ins>numero_paquete</ins>, monto, detalles) | `numero_paquete` |
| Ingrediente | **ingrediente** (<ins>id_ingrediente</ins>, nombre, unidad_medida, stock_actual, stock_minimo) | `id_ingrediente` |

La columna `rol` de usuario no viene de un atributo del EER: es el discriminador de la jerarquía y se explica en la Regla 9.

### Restricciones por tabla

| Tabla | Restricción | Columna | Regla de negocio que protege |
| :-- | :-- | :-- | :-- |
| evento | `CHECK (numero_asistentes > 0)` | numero_asistentes | No se monta un evento sin invitados |
| evento | `CHECK (estado IN ('programado','en_curso','finalizado','cancelado'))` + `DEFAULT 'programado'` | estado | Un evento nace programado y solo pasa por esos estados |
| usuario | `UNIQUE (usuario)` | usuario | Es la clave alternativa: dos personas no pueden entrar con el mismo nombre de acceso |
| usuario | `CHECK (fecha_nacimiento >= '1900-01-01')` | fecha_nacimiento | Evita años mal capturados |
| producto | `UNIQUE (nombre)` | nombre | El mesero elige el producto por su nombre; dos con el mismo nombre serían ambiguos |
| producto | `CHECK (categoria IN ('alimentos','bebidas','dulceria'))` | categoria | Las tres categorías de la entrevista |
| producto | `CHECK (precio >= 0)` | precio | Un precio negativo no tiene sentido; 0 sí, para cortesías |
| producto | admite `NULL` | descripcion | Atributo opcional: no todos los productos llevan texto en la carta |
| comanda | `CHECK (precio_cobrado >= 0)` | precio_cobrado | Igual que el precio |
| comanda | `CHECK (estado IN ('pendiente','en_preparacion','lista','entregada','cancelada'))` + `DEFAULT 'pendiente'` | estado | El ciclo de vida de una comanda |
| comanda | `DEFAULT now()` | fecha_hora | La comanda queda fechada al levantarla |
| comanda | admite `NULL` | detalles | Atributo marcado como opcional en el EER |
| pago | `CHECK (monto > 0)` | monto | Un pago de cero no es un pago |
| pago | `CHECK (forma_pago IN ('efectivo','tarjeta','transferencia'))` | forma_pago | Las formas de pago que acepta el salón |
| anticipo | `CHECK (monto > 0)` | monto | Igual que el pago |
| paquete | `CHECK (monto >= 0)` | monto | Igual que el precio |
| ingrediente | `UNIQUE (nombre)` | nombre | Clave alternativa: dos ingredientes con el mismo nombre partirían el stock en dos |
| ingrediente | `CHECK (unidad_medida IN ('g','ml','pieza'))` | unidad_medida | El stock y las recetas se capturan en la unidad base, para poder restarlos |
| ingrediente | `CHECK (stock_actual >= 0)` + `DEFAULT 0` | stock_actual | No se puede usar lo que no hay; un ingrediente nuevo empieza sin existencias |
| ingrediente | `CHECK (stock_minimo >= 0)` + `DEFAULT 0` | stock_minimo | Igual que el stock |

Todas las columnas son `NOT NULL` salvo `comanda.detalles`, `producto.descripcion` y las claves foráneas de relaciones con mínimo 0 (Regla 4).

## Regla 2: atributos compuestos

> Los atributos compuestos se descomponen en sus componentes simples: una columna por componente, y el atributo padre se elimina.

El modelo tiene cinco atributos compuestos, todos de fecha. En la Práctica 2 se modelaron compuestos porque el cliente consulta por día, mes y año por separado, así que los componentes **sí** deben existir como columnas. Aplicar la regla al pie de la letra, guardando tres `SMALLINT` sueltos y borrando la fecha, permitiría guardar el 31 de febrero y obligaría a reconstruir la fecha en cada comparación.

Por eso la regla se aplicó con una variante: el atributo padre se guarda con el tipo nativo del gestor, que valida la fecha, y cada componente es una **columna generada** (`GENERATED ALWAYS AS ... STORED`). Hay una columna por componente, como pide la regla, pero el gestor la calcula y nadie la puede escribir, así que nunca contradice a la fecha.

| Entidad | Atributo compuesto | Columna padre | Columnas por componente |
| :-- | :-- | :-- | :-- |
| Evento | Fecha | `fecha DATE` | `fecha_dia`, `fecha_mes`, `fecha_anio` |
| Usuario | Fecha de nacimiento | `fecha_nacimiento DATE` | `fecha_nacimiento_dia`, `fecha_nacimiento_mes`, `fecha_nacimiento_anio` |
| Comanda | Time Stamp | `fecha_hora TIMESTAMPTZ` | `fecha_hora_dia`, `fecha_hora_mes`, `fecha_hora_anio`, `fecha_hora_hora` |
| Pago | Time Stamp | `fecha_hora TIMESTAMPTZ` | `fecha_hora_dia`, `fecha_hora_mes`, `fecha_hora_anio`, `fecha_hora_hora` |
| Anticipo | Fecha | `fecha DATE` | `fecha_dia`, `fecha_mes`, `fecha_anio` |

```sql
fecha      DATE      NOT NULL,
fecha_dia  SMALLINT  GENERATED ALWAYS AS (EXTRACT(DAY   FROM fecha)::SMALLINT) STORED,
fecha_mes  SMALLINT  GENERATED ALWAYS AS (EXTRACT(MONTH FROM fecha)::SMALLINT) STORED,
fecha_anio SMALLINT  GENERATED ALWAYS AS (EXTRACT(YEAR  FROM fecha)::SMALLINT) STORED,
```

En los `TIMESTAMPTZ` los componentes se calculan en la zona `America/Mexico_City` (`fecha_hora AT TIME ZONE 'America/Mexico_City'`). Así una comanda de las 23:30 queda en el día del evento y no en el siguiente, que es lo que daría la hora UTC.

## Regla 3: atributos multivaluados

> Cada atributo multivaluado se convierte en una tabla aparte con la clave primaria de la entidad original como clave foránea más una columna para el valor. La clave primaria de esa tabla es la combinación de ambas.

| Entidad | Atributo multivaluado | Tabla resultante |
| :-- | :-- | :-- |
| Evento | Organizador/cliente | **evento_organizador** (<ins>*numero_evento*</ins>, <ins>organizador</ins>) — *numero_evento* → evento |

La clave compuesta impide registrar dos veces al mismo organizador en el mismo evento. La clave foránea usa `ON DELETE CASCADE`: un organizador no significa nada sin el evento al que describe.

En la primera versión del modelo, Ingredientes también era un atributo multivaluado de Producto y producía la tabla `producto_ingrediente (id_producto, ingrediente)`. Se cambió cuando el cliente pidió llevar el inventario: el ingrediente necesita stock y unidad propios, y el mismo ingrediente se comparte entre productos, así que en el EER pasó a ser la entidad **Ingrediente** (Regla 1) con la relación muchos a muchos *Receta* (Regla 5). Con la tabla multivaluada, "hielo" se habría repetido una vez por cada bebida, sin un solo stock del cual descontar.

## Atributos derivados

Las reglas no dicen qué hacer con los atributos derivados, así que se tomó un criterio: **no se guardan**. Un dato derivado cambia cada vez que cambia el dato del que sale, y guardarlo obliga a mantener la copia sincronizada; si alguna vez no se actualiza, la base tiene dos versiones distintas de la misma cosa. En su lugar se calculan en vistas:

| Entidad | Atributo derivado | Dónde queda |
| :-- | :-- | :-- |
| Evento | Número de mesas | Vista `v_evento` |
| Cuenta | Total acumulado | Vista `v_cuenta` |
| Cuenta | Saldo | Vista `v_cuenta` |
| Usuario | Edad | Vista `v_usuario` |
| Mesero | Propinas acumuladas | Vista `v_mesero` |
| Comanda | Precio | Vista `v_comanda`, como `precio_catalogo` |
| Producto | Disponible | Vista `v_producto` |
| Cuenta | Folio | Columna generada `cuenta.folio` |

El Folio es la excepción porque sale solo de columnas de la propia fila que nunca cambian (número de evento, número de mesa y secuencial). Como columna generada no se puede desincronizar y se puede buscar directo por folio.

Comanda tiene dos atributos de precio que no deben confundirse: `precio_cobrado` es un dato guardado, porque se copia del catálogo al levantar la comanda y ya no cambia aunque el producto suba de precio; `Precio` es el precio vigente del producto y por eso es derivado.

# Parte 4 — Transformación de relaciones

## Regla 4: relaciones uno a muchos

> La clave primaria del lado uno se propaga como clave foránea a la tabla del lado muchos. Si la cardinalidad mínima del lado muchos es 1, la clave foránea es `NOT NULL`; si es 0, admite nulos.

En la tabla, "mínimo del lado muchos" es la participación de la entidad que **recibe** la clave foránea: si toda comanda tiene que pertenecer a una cuenta, la columna no puede quedar vacía.

| # | Relación | Lado uno | Lado muchos (recibe la FK) | Clave foránea | Mínimo del lado muchos | `NULL` | Tabla resultante |
| :--: | :-- | :-- | :-- | :-- | :--: | :--: | :-- |
| R3 | *Atiende* | Mesero | Mesa | `mesa.id_mesero` | 1 | No | mesa |
| R4 | *Tiene* | Mesa | Cuenta | `cuenta.(numero_evento, numero_mesa)` | 1 | No | cuenta |
| R5 | *Genera* | Cuenta | Comanda | `comanda.(numero_evento, secuencial)` | 1 | No | comanda |
| R6 | *Levanta* | Mesero | Comanda | `comanda.id_mesero` | 1 | No | comanda |
| R7 | *Referencia* | Producto | Comanda | `comanda.id_producto` | 1 | No | comanda |
| R8 | *Prepara* | Bar/Cocina | Comanda | `comanda.id_bar_cocina` | 0 | Sí | comanda |
| R9 | *Cancela* | Cajero/Administrador | Comanda | `comanda.id_cajero_cancela` | 0 | Sí | comanda |
| R10 | *Recibe* | Cuenta | Pago | `pago.(numero_evento, secuencial)` | 1 | No | pago |
| R11 | *Maneja* | Cajero/Administrador | Pago | `pago.id_cajero` | 1 | No | pago |
| R12 | *Recibe propina* | Mesero | Pago | `pago.id_mesero_propina` | 0 | Sí | pago |
| R13 | *Recibe* | Evento | Anticipo | `anticipo.numero_evento` | 1 | No | anticipo |
| R14 | *Variante* | Producto (principal) | Producto (variante) | `producto.id_producto_principal` | 0 | Sí | producto |

Las relaciones identificadoras R1 y R2 también son uno a muchos, pero se transforman con la Regla 8.

Varias decisiones salen de aplicar la regla a casos que no son el ejemplo de libro:

- **Claves foráneas compuestas (R4, R5, R10).** Cuenta y Mesa son entidades débiles con clave de dos columnas, así que quien las referencia recibe las dos. En R4 la cuenta ya tiene `numero_evento` por su propia clave, de modo que solo se agrega `numero_mesa` y la clave foránea reutiliza la columna existente: `(numero_evento, numero_mesa)` → mesa. Con eso el gestor impide que una cuenta del evento 17 quede en una mesa del evento 22, algo que con una clave foránea de una sola columna no se podría expresar.
- **Atributo de relación (R12).** *Recibe propina* tiene el atributo Monto de propina. En una relación uno a muchos el atributo viaja junto con la clave foránea al lado muchos: `pago.monto_propina`. Como los dos son opcionales, se agrega `CHECK ((id_mesero_propina IS NULL) = (monto_propina IS NULL))` para que no exista una propina sin mesero ni un mesero sin monto.
- **Relación recursiva (R14).** *Variante* conecta Producto consigo mismo, así que la clave foránea apunta a la misma tabla. Se agrega `CHECK (id_producto_principal <> id_producto)` para que un producto no sea variante de sí mismo.
- **Relaciones hacia subtipos (R3, R6, R8, R9, R11, R12).** La clave foránea no apunta a usuario sino a la tabla del subtipo: `id_mesero` → mesero, `id_cajero` → cajero_admin. Esto solo es posible por la estrategia elegida en la Regla 9.
- **Restricciones que acompañan a las relaciones opcionales.** Que la clave foránea admita nulos no significa que el nulo pueda aparecer en cualquier momento. *Cancela* y *Prepara* están ligadas al estado de la comanda:
  - `CHECK ((estado = 'cancelada') = (id_cajero_cancela IS NOT NULL))`: una comanda está cancelada si y solo si un cajero o administrador la canceló.
  - `CHECK (id_bar_cocina IS NOT NULL OR estado IN ('pendiente','cancelada'))`: solo puede no tener estación si todavía no se prepara o si se canceló antes.

## Regla 5: relaciones muchos a muchos

> Se convierten en una tabla propia con las claves primarias de ambas entidades como claves foráneas. La clave primaria es la combinación de las dos y, si la relación tiene atributos, se agregan como columnas.

| # | Relación | Tabla resultante |
| :--: | :-- | :-- |
| R15 | *Incluye* (Paquete–Producto) | **paquete_producto** (<ins>*numero_paquete*</ins>, <ins>*id_producto*</ins>) — *numero_paquete* → paquete, *id_producto* → producto |
| R17 | *Receta* (Producto–Ingrediente) | **receta** (<ins>*id_producto*</ins>, <ins>*id_ingrediente*</ins>, cantidad_por_porcion) — *id_producto* → producto, *id_ingrediente* → ingrediente |

*Incluye* no tiene atributos propios: en la Práctica 2 se decidió que el catálogo dice qué trae un paquete, no cuánto, y las cantidades viven en la ternaria *Acuerda*. Las acciones referenciales son distintas en cada lado: al borrar un paquete se borra su contenido (`CASCADE`), pero un producto que forma parte de un paquete no se puede borrar (`RESTRICT`), porque eso cambiaría en silencio lo que el salón ofrece.

*Receta* **sí** tiene atributo propio, `cantidad_por_porcion`, que se agrega como columna como pide la regla, con `CHECK (cantidad_por_porcion > 0)`: un ingrediente que no se usa simplemente no va en la receta. Las acciones referenciales siguen el mismo criterio que *Incluye*: la receta es parte del producto y se borra con él (`CASCADE`), pero un ingrediente que alguna receta usa no se puede borrar (`RESTRICT`), porque dejaría productos con la receta incompleta sin que nadie lo note.

Con la receta guardada, el descuento del inventario queda en el gestor: el disparador `tg_comanda_stock` resta del `stock_actual` de cada ingrediente su `cantidad_por_porcion` cuando la comanda entra a preparación, una sola vez, y rechaza la comanda si algún ingrediente no alcanza. El `CHECK (stock_actual >= 0)` respalda la revisión si dos comandas compiten por el mismo ingrediente.

## Regla 6: relaciones uno a uno

> Elija entre tres estrategias: propagar la clave de la obligatoria a la opcional con `UNIQUE`, propagarla con `UNIQUE` y `NOT NULL` si ambas son obligatorias, o fusionar ambas entidades.

**No aplica.** El inventario no tiene ninguna relación con máximo 1 en los dos lados. La que más se acerca es *Referencia* (Comanda–Producto), donde la comanda apunta a un solo producto, pero un producto aparece en muchas comandas: es uno a muchos y se resolvió con la Regla 4.

Tampoco se forzó una relación uno a uno donde no la había. Una tentación sería tratar la propina como una entidad aparte ligada uno a uno con el pago, pero en el EER la propina es un atributo de la relación *Recibe propina*, no una entidad, y se resolvió como tal en la Regla 4.

## Regla 7: relaciones de orden superior

> Las relaciones ternarias o mayores se transforman en una tabla propia que incluye las claves primarias de todas las entidades participantes, más los atributos propios de la relación.

| # | Relación | Tabla resultante |
| :--: | :-- | :-- |
| R16 | *Acuerda* (Evento–Paquete–Producto) | **acuerdo** (<ins>*numero_evento*</ins>, <ins>*numero_paquete*</ins>, <ins>*id_producto*</ins>, cantidad_acordada) — *numero_evento* → evento, *numero_paquete* → paquete, *id_producto* → producto |

La clave primaria son las tres claves foráneas juntas porque las tres participaciones son `(0,N)`: ningún par determina al tercero. Si fuera solo `(numero_evento, id_producto)`, el evento 17 no podría acordar refrescos del Paquete Plata y también del Paquete Postres, que es justo el caso que hizo necesaria la ternaria en la Práctica 2. `cantidad_acordada` es `NOT NULL` con `CHECK (cantidad_acordada > 0)`: si no se acordó nada, simplemente no hay fila.

`acuerdo` **no** tiene clave foránea hacia `paquete_producto`. En la Práctica 2 se estableció que el catálogo es una base y no una lista cerrada: en un evento se pueden acordar productos que el paquete no traía. Si la clave foránea existiera, el gestor rechazaría justo lo que el negocio permite.

## Acciones referenciales

Cada clave foránea declara qué pasa si se borra o se cambia la fila a la que apunta. El criterio fue el mismo en todo el esquema:

| Acción | Cuándo se usó | Ejemplos |
| :-- | :-- | :-- |
| `ON DELETE CASCADE` | La fila hija es **parte** de la padre y no significa nada sin ella: entidades débiles, atributos multivaluados, tablas de relación y subtipos | mesa y cuenta → evento; evento_organizador → evento; paquete_producto → paquete; receta → producto; mesero → usuario |
| `ON DELETE RESTRICT` | La fila hija es **historial** que no debe perderse (lo que ya se cobró, se pidió o se pagó), o la padre no se debe quitar mientras alguien la use | comanda → cuenta; pago → cuenta; anticipo → evento; comanda → producto; receta → ingrediente; cuenta → mesa |
| `ON UPDATE CASCADE` | Claves que se propagan como parte de otra clave | numero_evento hacia mesa, cuenta y acuerdo |
| `ON UPDATE RESTRICT` | Identificadores de usuario: cambiarlos rompería el rastro de quién hizo qué | todas las claves foráneas hacia usuario y sus subtipos |

`SET NULL` no se usó: ninguna relación del modelo permite que una fila pierda a su referencia y siga siendo válida. Por ejemplo, una comanda sin la cuenta que la generó ya no se le puede cobrar a nadie.

# Parte 5 — Entidades débiles y jerarquías

## Regla 8: entidades débiles

> Si la dependencia es de identificación, la tabla lleva una clave primaria compuesta por la clave foránea de la entidad propietaria más el discriminador; la clave foránea es `NOT NULL` y normalmente con `ON DELETE CASCADE`. Si la dependencia es solo de existencia, la tabla conserva su propia clave primaria y agrega la clave foránea como `NOT NULL`.

Las dos entidades débiles del modelo dependen de Evento **por identificación**, así que las dos siguen la primera parte de la regla:

| Entidad débil | Discriminador (clave parcial) | Tabla resultante |
| :-- | :-- | :-- |
| Mesa | Número de mesa | **mesa** (<ins>*numero_evento*</ins>, <ins>numero_mesa</ins>, *id_mesero*) — *numero_evento* → evento, *id_mesero* → mesero |
| Cuenta | Secuencial | **cuenta** (<ins>*numero_evento*</ins>, <ins>secuencial</ins>, *numero_mesa*, nombre, folio, estado) — *numero_evento* → evento, *(numero_evento, numero_mesa)* → mesa |

```sql
CONSTRAINT pk_mesa PRIMARY KEY (numero_evento, numero_mesa),
CONSTRAINT fk_mesa_evento FOREIGN KEY (numero_evento)
    REFERENCES evento (numero_evento)
    ON DELETE CASCADE
    ON UPDATE CASCADE,
```

- **Clave compuesta.** La mesa 3 del evento 17 y la mesa 3 del evento 22 son filas distintas, y el gestor rechaza una segunda mesa 3 en el mismo evento.
- **`NOT NULL`.** Viene incluido: ninguna columna de una clave primaria puede ser nula, así que no puede existir una mesa sin evento.
- **`ON DELETE CASCADE`.** Si se borra un evento que todavía no ha operado (por ejemplo, uno que se canceló antes de la fecha), sus mesas y cuentas desaparecen con él, porque sin el evento no identifican nada.
- **`ON UPDATE CASCADE`.** Si se corrige el número de un evento, la corrección llega a sus mesas y cuentas.

### Cómo conviven `CASCADE` y `RESTRICT`

La cascada de la Regla 8 se detiene en cuanto hay historial. Comanda, Pago y Anticipo son entidades fuertes con dinero de por medio y apuntan a cuenta y a evento con `RESTRICT`. Por eso, si el evento 17 ya tiene comandas o pagos, intentar borrarlo falla completo: el gestor no borra las mesas y deja las comandas huérfanas, sino que rechaza toda la operación. Un evento ya trabajado se cierra cambiando su `estado`, no borrándolo.

Al borrar un evento, la cascada llega a cada cuenta por dos caminos: directo desde evento y a través de mesa. Aunque `cuenta → mesa` usa `RESTRICT`, se probó que PostgreSQL resuelve los dos caminos en la misma instrucción y borra el evento con sus mesas y cuentas. Fuera de esa cascada, el `RESTRICT` sigue impidiendo que se borre o se renumere una mesa que ya tiene cuentas.

## Regla 9: jerarquías

| Estrategia | Ventaja | Desventaja | Cuándo conviene |
| :-- | :-- | :-- | :-- |
| A. Tabla por supertipo y por subtipo | Sin redundancia ni valores nulos | Requiere combinaciones para consultar todo | Subtipos con muchos atributos propios |
| B. Tabla única con discriminador | Consultas simples y rápidas | Muchos valores nulos | Subtipos con pocos atributos propios |
| C. Tabla por subtipo, sin supertipo | No requiere combinaciones | Repite los atributos comunes | Especialización total y disjunta |

## Jerarquía de Usuario

### 1. Disyunción y completitud

**Usuario → {Mesero, Bar/Cocina, Cajero/Administrador}** es **disjunta** y **total**, como se definió en la Práctica 2:

- **Disjunta:** una persona tiene un solo rol a la vez. Esto sostiene la separación de responsabilidades del salón: quien cobra no puede ser quien recibe la propina de ese cobro.
- **Total:** todo usuario del sistema es personal del salón con un rol. Un usuario sin rol no tendría permisos ni nada que hacer.

### 2. Estrategia elegida: A, tabla por supertipo y por subtipo

A primera vista, la tabla de estrategias apunta a otra opción: los subtipos tienen **pocos** atributos propios (dos cada uno), lo que sugiere B, y la jerarquía es **total y disjunta**, lo que habilita C. Se eligió A porque el criterio que decide en este modelo no son los atributos, sino las **relaciones propias de cada subtipo**:

| Subtipo | Relaciones en las que participa solo él |
| :-- | :-- |
| Mesero | *Atiende*, *Levanta*, *Recibe propina* |
| Bar/Cocina | *Prepara* |
| Cajero/Administrador | *Maneja*, *Cancela* |

Seis relaciones dependen de que la clave foránea apunte **solo a usuarios de un subtipo**. Ya en la Práctica 2 se dijo que la jerarquía existe por eso: "si lo único distinto fueran los atributos, bastaría con un campo rol".

**Por qué no B (tabla única).** Con una sola tabla, `pago.id_mesero_propina` apuntaría a `usuario` y el gestor aceptaría una propina para alguien de cocina. Para impedirlo habría que agregar a cada tabla una columna `rol` fija por cada relación, o escribir un disparador por relación. Además, `turno_asignado`, `estacion_asignada`, `nivel_acceso` y `caja_asignada` quedarían nulas en dos de cada tres filas, sin forma declarativa de exigir que el mesero sí tenga turno.

**Por qué no C (sin supertipo).** Nombre, usuario, contraseña y fecha de nacimiento se repetirían en tres tablas. La clave alternativa Usuario tendría que ser única **entre las tres**, y ni `UNIQUE` ni `PRIMARY KEY` abarcan varias tablas: dos personas podrían quedar con el mismo nombre de acceso, una como mesero y otra como cajero. El inicio de sesión tendría que buscar en tres tablas sin saber de antemano en cuál está la persona.

**Patrones de consulta esperados.** La desventaja de A son las combinaciones, y en este sistema casi no hacen falta:

| Consulta frecuente | Con la estrategia A |
| :-- | :-- |
| Inicio de sesión (buscar por `usuario` y verificar contraseña) | Una sola tabla, `usuario`, sin combinaciones. Ya trae el `rol` para decidir qué pantallas mostrar |
| Comandas pendientes de una estación | `comanda` con `bar_cocina`, que es la combinación que la consulta necesitaría de todos modos |
| Propinas de un mesero, pagos de un cajero | Directo sobre `pago` por su clave foránea |
| Listado del personal con todos sus datos | Tres combinaciones; es una consulta administrativa y poco frecuente |

### 3. Tablas resultantes

| Tabla | Columnas | Claves |
| :-- | :-- | :-- |
| **usuario** | <ins>id_usuario</ins>, nombre, usuario, fecha_nacimiento (+ componentes), contrasena_hash, rol | PK `id_usuario`; `UNIQUE (usuario)`; `UNIQUE (id_usuario, rol)` |
| **mesero** | <ins>*id_usuario*</ins>, *rol*, turno_asignado | PK `id_usuario`; FK `(id_usuario, rol)` → usuario |
| **bar_cocina** | <ins>*id_usuario*</ins>, *rol*, estado, estacion_asignada | PK `id_usuario`; FK `(id_usuario, rol)` → usuario |
| **cajero_admin** | <ins>*id_usuario*</ins>, *rol*, nivel_acceso, caja_asignada | PK `id_usuario`; FK `(id_usuario, rol)` → usuario |

Los subtipos no tienen identificador propio: su clave primaria es la del supertipo, que es a la vez clave foránea. Propinas acumuladas, el atributo derivado de Mesero, se calcula en la vista `v_mesero`.

### El discriminador `rol`

| Propiedad | Valor |
| :-- | :-- |
| Tabla | `usuario` |
| Tipo | `VARCHAR(12) NOT NULL` |
| Valores permitidos | `'mesero'`, `'bar_cocina'`, `'cajero_admin'` (`CHECK ck_usuario_rol`) |
| Qué indica | El subtipo al que pertenece el usuario; es lo que se consulta al iniciar sesión para saber qué puede hacer |
| Se repite en | `mesero.rol`, `bar_cocina.rol` y `cajero_admin.rol`, cada uno fijo a su valor con `CHECK` y con `DEFAULT` para no tener que escribirlo |

Un discriminador suele ser propio de la estrategia B, pero aquí hace falta para que el gestor pueda **verificar las dos restricciones** de la jerarquía:

**Disyunción, de forma declarativa.** Cada subtipo repite el `rol` fijo a su valor y apunta a usuario con una clave foránea de **dos columnas**:

```sql
CREATE TABLE mesero (
    id_usuario      INTEGER      NOT NULL,
    rol             VARCHAR(12)  NOT NULL DEFAULT 'mesero',
    turno_asignado  VARCHAR(12)  NOT NULL,
    CONSTRAINT pk_mesero PRIMARY KEY (id_usuario),
    CONSTRAINT ck_mesero_rol CHECK (rol = 'mesero'),
    CONSTRAINT fk_mesero_usuario FOREIGN KEY (id_usuario, rol)
        REFERENCES usuario (id_usuario, rol)
        ON DELETE CASCADE
        ON UPDATE RESTRICT
);
```

Una fila en `mesero` solo puede apuntar a `(5, 'mesero')`, y esa pareja solo existe en usuario si el usuario 5 tiene rol mesero. Como cada usuario tiene un único rol, no puede aparecer en dos subtipos. `UNIQUE (id_usuario, rol)` en usuario es redundante como clave, porque `id_usuario` ya es único, pero hace falta porque una clave foránea solo puede apuntar a columnas declaradas únicas.

**Completitud, con un disparador diferido.** Que todo usuario tenga su fila de subtipo no se puede declarar con claves foráneas: usuario tendría que apuntar al subtipo y el subtipo a usuario, y ninguno de los dos se podría insertar primero. Se resolvió con disparadores de restricción `DEFERRABLE INITIALLY DEFERRED` sobre usuario (al insertar) y sobre cada subtipo (al borrar). Se revisan al hacer `COMMIT`, así que el usuario y su subtipo se insertan juntos en la misma transacción y, si falta el subtipo, se deshace todo.

### Lo que se sacrifica: el cambio de rol

En la Práctica 2 se dijo que una persona puede cambiar de rol con el tiempo y que lo que ya registró se queda a su nombre. Con este diseño, `ON UPDATE RESTRICT` impide cambiar el `rol` de un usuario que tiene fila de subtipo, y borrar su fila de mesero falla si ya levantó comandas. El historial queda protegido, pero el cambio de rol no se puede hacer con un `UPDATE`.

Se prefirió así porque la disyunción es la regla que sostiene el control del dinero, y un cambio de rol es un evento raro que puede pasar por un procedimiento administrativo. Si en el futuro el cambio de rol se vuelve frecuente, la solución es separar "quién es" de "qué rol tiene en qué periodo" con una tabla de historial de roles. Eso queda fuera del modelo EER actual.

## Lo que el esquema no puede garantizar

Igual que el diagrama EER tenía reglas que no podía dibujar, hay cardinalidades y reglas que el esquema no hace cumplir. Se dejan escritas para que se validen en la aplicación:

| Regla | Por qué no está en el esquema |
| :-- | :-- |
| Todo evento tiene al menos una mesa (*Pertenece*, mínimo 1 del lado de Evento) | El evento se registra al contratarse, semanas antes de que se monten las mesas. Exigirlo impediría capturar eventos futuros |
| Todo producto lleva al menos un ingrediente (*Receta*, mínimo 1 del lado de Producto) | Igual que *Incluye*: la receta se captura después de dar de alta el producto. Un producto sin receta no descuenta inventario y la vista lo muestra siempre disponible |
| Todo paquete incluye al menos un producto (*Incluye*, mínimo 1 del lado de Paquete) | Se podría exigir con un disparador diferido como el de la jerarquía, pero el catálogo se arma en varias capturas y bloquearlo no aporta |
| Máximo de mesas que caben en el salón | Depende del salón y del acomodo, no es una constante del modelo |
| El mesero que recibe la propina es el que atendió la mesa | El EER no lo pide; un mesero puede cubrir a otro |
| Cambio de rol conservando el historial | Ver la sección anterior |

Tres reglas que el diagrama de la Práctica 2 tampoco podía mostrar **sí** quedaron en el gestor: el `precio_cobrado` se copia solo del catálogo al levantar la comanda y no se puede modificar después (disparador `tg_comanda_precio`), una variante no puede tener variantes (disparador `tg_producto_variante`), y al preparar una comanda se descuenta su receta del inventario sin dejar el stock en negativo (disparador `tg_comanda_stock` y `CHECK` de `ingrediente`).
